# AGENTS.md — working in the Zazzles vulnerability lab

A deliberately vulnerable Next.js testbed for SAST/SCA tool evaluation. Everything here is intentional: the flaws, the pins, and the safe controls. Your job is to extend it without eroding its ground truth.

**Read this file first, every session. Details live in [`docs/`](docs/README.md) — especially [adding-scenarios.md](docs/adding-scenarios.md), [architecture.md](docs/architecture.md), and [validation-and-sanitization.md](docs/validation-and-sanitization.md).**

## Non-negotiable invariants

1. **Never "fix" a vulnerable route.** The flaws are the product. If a test proves a flaw stopped being exploitable, that is a regression — restore it.
2. **Never upgrade pinned vulnerable dependencies.** `targets/react2shell` (next 15.0.4 / React 19.0.0, CVE-2025-66478) and the main app's Next 13.4.19 / React 18.2.0 stay pinned. Retiring a scenario is a dedicated, documented change.
3. **Safe controls are scoped claims.** A control proves "this pattern defeats this flaw for identical input" — never describe one as universally secure. Validation complements parameterization; it never replaces it.
4. **Safety rails stay:** loopback-only binds, synthetic data, harmless markers (`42`, `zazzles-*-marker`), no real credentials or sensitive files in demos or docs.
5. **Ground truth is generated, never hand-edited** (see below).

## Commands

```bash
corepack enable && pnpm install     # pnpm 11.25.0 is pinned via packageManager
pnpm dev                            # main lab → 127.0.0.1:3000
pnpm build:react2shell && pnpm start:react2shell   # SCA fixture → 127.0.0.1:3001

pnpm lint                           # ESLint (pages, components, lib, tests, scripts)
pnpm test                           # Vitest unit suite (direct handler imports, real PGlite)
pnpm test:http                      # end-to-end pairs vs a running `pnpm start`
pnpm test:browser                   # Playwright/Chromium (needs `pnpm exec playwright install chromium` once; auto-starts a built server)
pnpm test:react2shell               # RSC runtime execution marker vs running fixture
pnpm scenario:check / audit:check   # ground-truth gates (below)
```

Full matrix and what each proves: [docs/setup-and-testing.md](docs/setup-and-testing.md). CI (`.github/workflows/ci.yml`) runs the same set — it must stay green.

## The ground-truth system

`lib/catalog.json` is the single source of truth for scenarios (IDs, sources, safe controls, docs, tests). Three committed artifacts are **generated from it and the dependency graph**:

| Artifact | Generated by | Verified by |
| --- | --- | --- |
| `tests/expected-hashes.json` — SHA-256 of every catalog-registered route | `pnpm scenario:update` | `pnpm scenario:check` |
| `tests/expected-scanner-findings.json` — per-source must-find / must-not-flag + CWE | `pnpm scenario:update` | `pnpm scenario:check` |
| `tests/expected-audit.json` — `pnpm audit --prod --json` snapshot | `pnpm audit:update` | `pnpm audit:check` |

Rules:

- After any reviewed change to scenario sources or dependencies, re-snapshot with the matching `*:update` command **in the same commit** as the change that justifies it.
- A manifest update with no corresponding source change will not pass review; a source change without the manifest update fails `scenario:check`/`audit:check`.
- `pnpm audit --prod` exiting nonzero is **correct** (the pins are the scenario). Only drift from the snapshot fails.

## Adding a vulnerability scenario

Checklist (expanded in [docs/adding-scenarios.md](docs/adding-scenarios.md)):

1. **Stable ID** `<CATEGORY>-<number>` (`JS-`, `OS-`, `FS-`, `SQL-`, `XSS-`, `SSRF-`, `REDIR-`, `SCA-`, `DEMO-`). IDs never change once shipped.
2. **Unsafe source and safe control in separate files**, following the existing pairs (`pages/api/sql/{unsafe,safe,zod}/…`, `pages/xss/{unsafe,safe,sanitized}/…`). Mark the sink with a comment: `// <ID> / <CWE>: …`.
3. **The safe control must accept the identical payload and keep it inert** — derive the protection from a named pattern ([validation-and-sanitization.md](docs/validation-and-sanitization.md)), not from rejecting the payload. Input validation on both sides must not neutralize the attack (the exploit must still work on the unsafe side).
4. **Catalog entry** in `lib/catalog.json`: `source`, `safeControl` (primary), optional `safeControls` array (additional library-based controls), `documentation`, `test`, `flow`, `runtime`, `cwe`, `expectedFinding: true`. Explanatory pages with no sink are `status: "demonstration"` / `expectedFinding: false`.
5. **Documentation section** in the matching `docs/vulnerabilities/<module>.md` following the anchor contract: `#<id>`, `#<id>-agent` (compact, self-contained expected finding), `#<id>-student`, `#<id>-exploit` (**Burp Suite + Postman + curl** variants, verified commands only), `#<id>-safe` (vulnerable-vs-protected table **and why**), `#<id>-tests`. Add the row to the module's Contents table and to `docs/vulnerabilities/index.md`.
6. **Tests, both directions**: unit (`tests/unit/*.test.mjs`, import handlers directly, use `request()` from `helpers.mjs`), HTTP (`scripts/test-http.mjs` pairs + route sweep), and browser (`tests/browser/…`) for anything that executes client-side — assert a marker property **is set** on the unsafe page and **provably unset** on the safe page.
7. **Re-snapshot** (`pnpm scenario:update`) and commit manifests with the change.

Gotchas learned the hard way:

- `JSON.stringify` escapes `"` → `\"`: payloads that break out of inline `<script>` (XSS-003 style) must avoid double quotes (single-quoted attribute + backtick string).
- Next.js normalizes `//host` `getServerSideProps` redirect destinations to same-site paths — the open-redirect exploit is the absolute-URL form.
- InnerHTML-inserted `<script>` elements do not execute; use event-handler attributes (`<img src=x onerror=…>`) for execution markers.
- `dangerouslySetInnerHTML` content passes through verbatim in SSR — scope no-handler assertions to the rendered container, not the whole document (`__NEXT_DATA__` carries raw props).

## Adding a safe operation / protected route

1. Pick the pattern from [docs/validation-and-sanitization.md](docs/validation-and-sanitization.md) (Zod for shape validation, bound SQL parameters, `execFile` + argument vector, exact-string allowlists, DOMPurify for rich text, React text nodes otherwise, origin policy before fetching, relative-only redirects).
2. Mirror an existing control; respond identically to the paired vulnerable route for the **same payload**, with the payload verifiably inert (echoed, stored literally, or stripped-of-execution).
3. Register it: add to the scenario's `safeControls` in the catalog (this hashes it and exports it as a must-not-flag row), document it in the scenario's `-safe` section, and cover it in unit + HTTP tests.
4. `pnpm scenario:update` afterwards.

## Adding a regular feature

Keep UI conventions (`components/LabLayout`, `components/ApiConsole`, catalog-driven pages). Do not touch scenario source files incidentally — feature work that refractors a hashed file requires the `scenario:update` re-snapshot and a justification in the commit. Prefer additive changes.

## Before you commit

```bash
pnpm lint && pnpm test && pnpm scenario:check && pnpm audit:check
pnpm build && (pnpm start &)   # then: pnpm test:http && pnpm test:browser
pnpm build:react2shell && (pnpm start:react2shell &)   # then: pnpm test:react2shell
```

All green → commit with a message that says *why*, push. `main` holds verified work; anything exploratory goes on a feature branch first. Preserve upstream attribution (Eric / e-tang) in docs and UI.
